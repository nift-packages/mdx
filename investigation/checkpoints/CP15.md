# CP15 — normal installed-site batch orchestration

`prepare` is the required pre-build batch boundary. File-backed `html(input(...))`
only consumes prepared artifacts and registers all returned dependencies; it
cannot fall back to per-page subprocesses. Inline parse/html retains explicitly
one-off semantics. One worker executes documents serially with a bounded heap
and deadline, providing deterministic result order and independent IDs.

Linux invocation instrumentation confirms one helper invocation plus one cheap
Node capability probe for the whole build, at every scale and on unchanged
builds. A1,000-document mixed batch matches scalar HTML for five syntax classes;
one failure preserves all other result identities/output. Existing installed
facade/transitive dependency tests prove real project integration.

Benchmark fixture:~1 KiB prose/GFM/list/code pages;20% shared MDX imports,20%
component adapters. Actual Git-installed package,100/500/1,000 tracked Nift
targets. Measured wall time includes pre-hook parsing+graphs, serialization,
capability probe, helper startup/compile/evaluate/static render, prepared record
updates, target parsing/dep registration and HTML output. No-change builds verify
all targets up to date. These synthetic fixtures are not the Capgo corpus.

Detailed stage sums and invocation counts are recorded in CP15-site-results.json.
Target-side parsing happens again on cold builds; warm pre-hook parsing still
dominates. Batch architecture is certified, but acceptable Capgo-scale latency
is not. Do not advertise the helper's timing as full-build performance.
